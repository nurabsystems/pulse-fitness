Pulse Fitness

The Evolution to Fullstack Architecture

From hardcoded static data to a live, secure, cloud-hosted application. This is the technical journey of how Pulse Fitness evolved from Week 1 to Week 3.

The Past (Week 1 & 2)

Previous Architecture: The "Mock" Era

How Data Was Handled

  • Hardcoded Arrays: Data lived inside src/data/trainers.js.
  • No Database: If you added a trainer, you had to write code and redeploy.
  • Frontend Heavy: The browser held all the information.

Security & Auth

  • No Real Login: Just a fake "localStorage" username.
  • No Passwords: Anyone could spoof the session.
  • No API Security: Everything was exposed to the client.

It worked visually, but it wasn't a real application. It was a mockup.

The Present (Week 3)

New Architecture: The "Fullstack" Era

How Data is Handled Now

  • Cloud Database: Data lives in PostgreSQL (Neon).
  • REST API: The frontend fetches JSON from Express (Render).
  • Scalable: You can add 1,000 trainers without touching code.

Security & Auth

  • Real Authentication: Better Auth with hashed passwords.
  • HTTP-Only Cookies: Secure, cross-origin sessions (JWT).
  • API Security: CORS blocks unauthorised domains.

Why the New Architecture Wins

  • Persistence: Data survives refreshes and browser changes because it lives in the cloud, not the browser cache.
  • Security: Passwords are never stored in the frontend. They are hashed in the backend and secured with HTTP-only cookies (blocking XSS attacks).
  • Scalability: Multiple users can interact with the database simultaneously.
  • Production Ready: This is how real companies build web apps (Client ➔ API ➔ Database).

Database & Schema Design (Drizzle ORM)

We moved from hardcoded arrays to a real relational database using Drizzle ORM.

// server/src/db/schema.js export const trainers = pgTable('trainers', { id: uuid('id').primaryKey().defaultRandom(), name: text('name').notNull(), specialty: text('specialty').notNull(), bio: text('bio').notNull(), image: text('image').notNull(), rating: integer('rating').notNull().default(5), });
  • Defined tables for trainers, classes, pricing, and users.
  • Used Drizzle Kit to generate SQL migrations and push them to Neon.

Data Seeding & Migration

To populate the cloud database, we wrote a seed script.

// server/src/db/seed.js await db.delete(classes); await db.delete(trainers); const inserted = await db.insert(trainers).values(trainersData).returning(); console.log(`Inserted ${inserted.length} trainers`);
  • Run via npm run db:seed.
  • The database now holds 6 trainers, 12 classes, and 3 pricing tiers natively in PostgreSQL.

  • Database: Sessions are stored in the Postgres session table.
  • Client-side: The React app uses the useSession hook to know who is logged in.

Overcoming Technical Challenges

  • Dependency Hell: Better Auth conflicted with Drizzle's peer dependencies. Fixed using .npmrc and exact version pinning.
  • Schema Drift: The auto-generated migration missed tables. Fixed by manually writing the CREATE TABLE SQL in Neon.
  • Cross-Origin Sessions: Vercel and Render are different domains. The cookie failed to save. Fixed by setting sameSite: "none" and secure: true.
